## 1 引言

### 1.1 编写目的

本文档描述 AgentTrace 的功能需求与非功能需求，作为后续软件设计、测试与验收的依据。预期读者：指导教师、开发者本人（单人开发）。

### 1.2 项目背景

基于大语言模型（LLM）的 Agent 软件正快速发展，但其运行过程是不透明的"技术黑箱"：开发者难以知晓 Agent 每一步调用了什么工具、LLM 返回了什么、Token 消耗与失败发生在哪里。这带来代码确认与验收难题，也加剧"认知外包"风险。SWEBOK v4 新增"软件工程运营"知识领域，可观测性是其核心内容。

本项目开发一个轻量级 Agent 运行可观测性工具：Python SDK 以非侵入方式拦截并记录 Agent 运行事件，配合 Web 查看器实现运行过程的回放、查询与统计，帮助 Agent 开发者定位问题、评估成本、验证行为。

**项目来源**：本项目为《软件工程》课程项目实践作业（2026 年秋季学期，个人选题），2026 年 9 月立项，计划 2026-12-31 前交付。

### 1.3 术语与缩略语

| 术语 | 定义 |
|------|------|
| Agent | 基于大语言模型、能自主规划并调用工具完成任务的智能体软件 |
| LLM | Large Language Model，大语言模型 |
| Trace | 一次 Agent 任务运行的完整记录 |
| Span/Event | Trace 内的单个事件节点（LLM 调用、工具调用或决策步骤） |
| Token | LLM 处理文本的计量单位，用于成本统计 |
| Mock 模式 | 用预存的 LLM 应答数据代替真实 API 调用，支持离线运行 |

## 2 任务概述

### 2.1 项目目标

总目标见上文 1.2。可量化目标（验收锚点）：

- G1：Agent 开发者以 ≤3 行代码接入 SDK，即可获得完整运行记录；
- G2：一次 Agent 任务的 LLM 调用、工具调用、决策步骤 100% 被记录并可回放；
- G3：SDK 埋点引入的额外开销不超过 10%（初值，M4 性能测试后定稿）；
- G4：全部需求可追溯到测试用例（需求-用例-测试追踪表）。

### 2.2 用户特点

目标用户：使用 Python 编写 Agent 应用的开发者（学生、个人开发者）。具备基本编程能力，无数据分析背景，不希望为观测工具学习复杂部署。

需求获取方式：竞品/相关工作分析（附录 A.1）+ 开发者自身体验（dogfooding，附录 A.2，随开发持续记录）。痛点结论：

1. Agent 运行黑箱：任务失败时难以定位是 LLM 返回异常、工具调用出错还是决策逻辑问题；
2. 成本不可见：Token 消耗分散在多次调用中，无法归集到任务与步骤级别；
3. 现有工具缺乏轻量选项：或绑定云服务与特定框架（LangSmith），或自托管部署面向团队（Langfuse），或面向 ML 评估场景（Phoenix），缺少"单机、离线、零配置"的个人开发者方案（详见附录 A.1）。

### 2.3 运行环境

| 项目 | 环境 |
|------|------|
| SDK 运行环境 | Python 3.11+；Windows / macOS / Linux 跨平台（以 Windows 为主验证环境） |
| 服务端 | Python 3.11+，FastAPI |
| 存储 | SQLite 3（单文件，零部署） |
| 查看器 | 现代浏览器（Chrome/Edge 最新版） |
| 开发环境 | Windows 11 + Git + VS Code + GitHub Actions |

### 2.4 约束与限制

1. 单人开发，周期约 16 周（2026-09 至 2026-12）；
2. SDK 尽量零第三方依赖（标准库优先），降低接入成本；
3. 演示与测试不依赖真实 LLM API（内置 Mock 回放模式）；
4. 遵循课程要求：明确的开发方法（单人 Scrum + TDD）、专业工具链（Git/CI/PlantUML）。

### 2.5 假设与依赖

- 假设被观测 Agent 为 Python 编写，且 LLM 调用与工具调用可被函数级拦截；
- 不假设用户 Agent 使用特定框架（如 LangChain），拦截发生在函数级；OpenAI 兼容接口仅作为内置 demo Agent 的默认适配对象；

## 3 功能需求

### 3.1 功能结构

系统分为四部分（功能结构图源文件：`models/function-structure.puml`）：

1. **SDK 拦截层**（F1/F2）：装饰器与上下文管理器接入，拦截 LLM 调用、工具调用并记录决策步骤，支持流式（SSE）响应记录与 Mock 离线模式；
2. **持久化存储**（F3）：SQLite 落盘，支持按时间/状态过滤；
3. **Web 查看器**（F4/F5）：Trace 列表页、时间线详情页、统计总览页；
4. **示例 Agent**（F6）：课程答疑 + 笔记整理双工具，Mock/真实 API 可切换。

> 注：全部建模图使用 PlantUML 文本源文件维护（满足作业"可编辑电子版源文件"要求），可用 VS Code PlantUML 插件或 plantuml.com 在线服务渲染导出图片。

### 3.2 用户角色

| 角色 | 说明 |
|------|------|
| Agent 开发者 | 唯一核心角色：接入 SDK、查询与回放 trace、查看统计 |

### 3.3 功能需求条目

**F1 拦截接入（SDK）**
- FR-1.1 系统应提供装饰器与上下文管理器两种接入方式，接入代码不超过 3 行；
- FR-1.2 拦截不应要求修改 Agent 业务逻辑代码本身；
- FR-1.3 系统应支持 Mock 模式：无真实 LLM API 时以预存应答运行并照常记录。

**F2 Trace 数据模型**
- FR-2.1 系统应记录每次 LLM 调用的输入、输出、Token 消耗与耗时；
- FR-2.2 系统应记录每次工具调用的函数名、参数、返回值与异常信息；
- FR-2.3 一次任务的所有事件应按树形时间线组织，可追溯父步骤；
- FR-2.4 事件应在产生后 1 秒内写入本地存储，进程异常退出时最多丢失最后一条；
- FR-2.5 对流式（SSE）的 LLM 响应，系统应记录增量累计的输出内容与 Token 统计，并在流结束时完成写回。

**F3 持久化存储**
- FR-3.1 系统应将 trace 持久化至 SQLite，进程重启后可查询；
- FR-3.2 系统应提供按时间、状态（成功/失败）过滤 trace 的能力。

**F4 Web 查看器——时间线回放**
- FR-4.1 查看器应提供 trace 列表页，展示时间、状态、步数、Token 总量；
- FR-4.2 查看器应提供单条 trace 的时间线详情页，按发生顺序展示各事件，失败事件醒目标注；
- FR-4.3 详情页应展示每个事件的完整输入/输出内容；
- FR-4.4 对流式输出的事件，详情页应展示聚合后的完整输出及其累计 Token 消耗。

**F5 统计总览**
- FR-5.1 系统应统计并展示总 Token 消耗、成功率、平均步数、失败类型分布。

**F6 示例被测 Agent（演示载体）**
- FR-6.1 系统应附带"课程学习助手"双工具示例 Agent（工具一：课程答疑——LLM 依据课程资料回答提问；工具二：笔记整理——将答疑内容归纳为结构化学习笔记），作为功能演示与集成测试载体；
- FR-6.2 示例 Agent 应支持 Mock 模式离线运行，并支持切换为真实 LLM API。

### 3.4 用例描述

**UC-01 记录 Agent 运行（核心用例）**

| 项目 | 内容 |
|------|------|
| 参与者 | Agent 开发者 |
| 前置条件 | 已安装 SDK；Agent 代码可运行 |
| 基本流 | ① 开发者在 Agent 入口添加装饰器 → ② 运行 Agent 任务 → ③ 系统拦截 LLM/工具/步骤事件 → ④ 事件写入 SQLite → ⑤ 任务结束生成完整 Trace |
| 备选流 | 4a. 写入失败 → 内存缓冲重试，仍失败则在控制台告警且不影响 Agent 运行 |
| 后置条件 | 本次任务生成一条可查询的 Trace |

**UC-02 回放与查看时间线**

| 项目 | 内容 |
|------|------|
| 参与者 | Agent 开发者 |
| 前置条件 | 已存在至少一条 Trace 记录（FR-3.1） |
| 基本流 | ① 开发者以一条命令启动查看器 → ② 系统展示 Trace 列表（时间、状态、步数、Token 总量）→ ③ 开发者选择某条 Trace → ④ 系统展示时间线详情页，按发生顺序展示各事件及完整输入/输出、耗时、Token → ⑤ 开发者逐事件检查执行过程 |
| 备选流 | 2a. 无任何 Trace → 空态提示并引导先运行示例 Agent；2b. 开发者按时间/状态过滤列表（FR-3.2）；4a. 事件为流式输出 → 展示聚合后完整输出与累计 Token（FR-4.4） |
| 后置条件 | 开发者了解该次任务的完整执行过程 |

**UC-03 查看统计总览**

| 项目 | 内容 |
|------|------|
| 参与者 | Agent 开发者 |
| 前置条件 | 存在历史 Trace 记录 |
| 基本流 | ① 开发者打开统计总览页 → ② 系统汇总展示总 Token 消耗、成功率、平均步数、失败类型分布（FR-5.1） |
| 备选流 | 2a. 无数据 → 显示空态与引导说明 |
| 后置条件 | 开发者掌握 Agent 运行的成本与质量整体状况 |

**UC-04 定位失败步骤**

| 项目 | 内容 |
|------|------|
| 参与者 | Agent 开发者 |
| 前置条件 | 存在状态为失败的 Trace |
| 基本流 | ① 开发者在列表按"失败"过滤 → ② 打开该 Trace 时间线 → ③ 失败事件以醒目标注呈现（FR-4.2）→ ④ 查看该事件的完整输入/输出/异常信息（FR-4.3）→ ⑤ 判定根因（LLM 返回异常 / 工具报错 / 决策逻辑问题） |
| 备选流 | 1a. 无失败 Trace → 提示全部成功；4a. 失败发生在流式响应中 → 查看聚合输出定位中断位置（FR-4.4） |
| 后置条件 | 定位到具体失败事件及其原因 |

## 5 数据需求

### 5.1 概念数据模型

核心实体：Trace（一次任务）1..* Span（事件：LLM 调用/工具调用/步骤），Span 树形自关联（parent_id）。

主要属性——Trace：id、name、status（running/success/failed）、start/end_time、total_tokens、error；Span：id、trace_id、parent_id、type（llm/tool/step）、name、input、output、status、token_in/out、duration_ms、is_stream、created_at。

类图源文件：`models/class-model.puml`。

### 5.2 接口需求

- SDK 公开接口（草案）：`@agenttrace.trace()` 装饰器、`with agenttrace.session():`、`agenttrace.log_step()`
- REST API（草案）：`GET /traces`、`GET /traces/{id}`、`GET /stats`

## 附录 A 需求获取记录

### A.1 竞品/相关工作分析（2026-09）

| 工具 | 性质 | 优势 | 对本项目目标场景（单机/离线/轻量）的不足 |
|------|------|------|------------------------------------------|
| LangSmith | LangChain 官方云平台（闭源） | 功能全面：trace、评估、数据集、监控；与 LangChain/LangGraph 无缝集成 | 以云服务为主，数据出本地；与 LangChain 生态深度耦合，非该框架的 Agent 接入成本高 |
| Langfuse | 开源 LLM 工程平台 | 可自托管、隐私友好；trace/prompt 管理/评估功能完整 | 自托管需部署服务端与数据库，面向团队协作场景；对单人单机、离线使用过重 |
| Arize Phoenix | 开源 LLM 观测（OpenInference 标准） | 开放标准、notebook 优先、本地可用 | 依赖栈较重，核心场景偏评估与实验工作流；快速接入、离线演示非其设计目标 |
| OpenTelemetry | 通用可观测性标准/框架 | 行业标准、语言与后端无关 | 通用 tracing 语义，无 Token/提示词/工具调用等 LLM 一等公民概念；手工埋点与配置繁琐 |
| LLM API 代理类（Helicone、LiteLLM 等） | API 代理层记录 | 代理即接入、基本不改代码 | 只能看见 API 层调用，看不到 Agent 决策步骤与工具调用树；代理本身需额外部署 |

**分析结论（差异化定位依据）**：

1. 多个成熟商业/开源工具的存在，证明"Agent 运行可观测"是真实且已被市场验证的需求（对应作业"背景具有实际意义"）；
2. 现有工具的共同空白：**单机本地、离线可用（mock）、零/近零依赖、函数级拦截不绑定框架、SQLite 单文件存储、一条命令启动查看器**——即个人开发者的"最小可用观测"方案；
3. 本项目不与上述产品竞争功能全面性，定位为该空档的轻量实现，并在课程场景下完整实践软件工程过程。
