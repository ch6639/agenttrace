## 2. 本轮修复和性能结论

1. **Token 汇总避免反复扫描整棵树。** 普通 Span 写入在同一事务中按库内提交前后差值更新；
   同批 Trace UPSERT 覆盖聚合值时重算。按实际存储快照处理重复 ID、Token 减少和失败回滚，
   大批量读取按 500 个绑定参数分块。默认 WAL + FULL 和逐事件确认保持不变。
2. **Windows 首次安装编码修复。** 新 venv 的 pip 24 默认按 GBK 读取中文锁文件时失败；
   增加文件编码声明后，原生新环境安装成功，无需修改系统编码设置。
3. **可复现发布门禁。** CI 增加安装后正式 CLI + HTTP 验收，保留测试结果与安装报告；
   支持 `codex/**` 分支触发和手动触发。
4. **在线验收工具。** 三个真实请求覆盖普通/SSE/调用方主动取消，每次输出上限默认 64、
   最大 128 Token；密钥仅从环境读取，报告不记录密钥、原始异常或正文。
   工具本身的五个协议替身测试属于离线测试，不能冒充在线证据。

3000 个 Span 的 Token 算法对照：旧全树重算总计 740.837ms，差值算法 393.319ms；
最后 100 条平均每条 0.33492ms → 0.10288ms。对照使用 WAL + NORMAL 以隔离 fsync 成本，
只说明该算法改善，不作为默认 durable 达标证据。

默认 durable 的剖析中，1111 次 SQLite 事务退出约 483ms，占剖析总时间约 72.5%。
同步提交是当前主要成本；短任务仍超标。最新矩阵中 durable 20ms 多步骤额外约 14.90ms，
200ms 多步骤额外约 17.94ms。样本受磁盘、调度和后台负载影响，不以不同时间的矩阵证明因果。
10/15 原始结果和本轮优化前样本均保留，不只挑选低开销场景；async 的低业务延迟也不能代替
durable 的持久性承诺。后续 M4 应继续测代表性真实负载及持久提交策略，阈值修订须明确记录。

## 3. 复现步骤

在仓库根目录、已安装开发依赖的环境执行：

```bash
python -m ruff check .
python -m pytest --cov=agenttrace --cov=server --cov-fail-under=70
cd web
npm ci
npm run build
cd ..
python scripts/build_wheel.py
python scripts/verify_wheel.py dist/agenttrace-0.1.0-py3-none-any.whl
python scripts/verify_install.py dist/agenttrace-0.1.0-py3-none-any.whl
python scripts/performance_suite.py --iterations 30 --output docs/performance-closeout-2026-10-22.json
python -m scripts.profile_ingestion --output docs/ingestion-profile-2026-10-22.json
```

在线验收：在本机配置 `OPENAI_API_KEY`、`OPENAI_MODEL`、可选 `OPENAI_BASE_URL` 后执行
`python -m scripts.verify_online`。缺配置退出 2，检查失败退出 1，全通过退出 0。调用方取消
允许缺少 usage，但需标记 Token 估算；不将主动取消冒充服务端故障。
