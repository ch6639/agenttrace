## 2. 持久性语义与代价

默认零配置选择 `durability="durable"`。事件经管线写锁进入 SQLite 事务，COMMIT 成功后
记录调用返回；根 Trace 聚合与根 Span 作为一个逻辑根事件同事务更新，避免两次 fsync
和“有 Trace 无根事件”的中间状态。占位 Span 在进入观测上下文时提交，终态在退出时提交。
已确认事件不依赖 flush 或 atexit 才持久化；强杀发生在当前未确认事务中时，该事务回滚。
强杀不会伪造根任务的成功/失败终态，未结束任务保持 running，查看器可提示疑似中断。

以上保证针对健康存储中已经成功完成记录的事件；尚在消费的流式输出在调用方内存中聚合，
未完成流的全部输出并未被承诺逐 chunk 持久化。写入故障/锁冲突重试耗尽时继续遵守 NFR-3
旁路降级，diagnostics 失败计数增加、flush 返回 False，不能把该次写入当作成功。
SQLite 单次锁等待 200ms，最多重试 3 次，错误日志不输出底层异常文本或事件输入。

显式 `agenttrace.init(durability="async")` 保留原有队列与后台批量模式；其优势是业务线程
延迟低，代价是强杀时队列和在途批可能丢失多条。32 是触发阈值，不是丢失上限。
未将 async 测试结果冒充 durable 的持久性或性能结果。

生命周期：应在任务外调用 init/shutdown，并 await 活跃异步子任务。flush/shutdown 在
持久写入尚未完成时也遵守 timeout，超时不关闭仍在使用的连接。diagnostics 和 flush
在 shutdown 后仍保留本轮写失败/丢弃信号，下一次 init 才开始新一轮统计。

## 3. 本地回归结果

- **79 项测试通过，SDK + server 覆盖率 95.05%，ruff 通过，pip check 通过。**
- 当前 Windows / Python 3.11.9 已实际运行。CI 配置扩展至 Ubuntu/Windows × Python
  3.11/3.12，远程任务未触发，未声称其他平台已验证。
- 原有 SDK 行为、SSE 替身、Mock 子进程、API 契约均回归通过；未调用真实收费 API。
- 前端构建通过：主 JS 489.60 KB / gzip 165.28 KB；统计图 JS 445.12 KB / gzip 152.03 KB；
  CSS 367.71 KB / gzip 50.10 KB。统计图从首屏拆出，仍与应用同端口离线托管。
- 浏览器：1001 条记录的分页列表就绪 949 ms，其中查询+DOM 更新 193 ms；统计页的
  懒加载图表、中文组件和四项指标验证通过。该样本未强制清空所有缓存，不能替代完整
  冷启动矩阵。证据见 [浏览器测量](browser-performance.json) 与
  [统计页截图](screenshots/viewer-improved-stats.jpg)。

复现主要命令（仓库根目录；前端另进入 web）：

```bash
python -m pip install -r requirements-dev.lock
python -m pip install -e ".[dev,server]"
ruff check .
pytest --cov=agenttrace --cov=server --cov-fail-under=70 --cov-report=term-missing
python scripts/performance_suite.py --iterations 20
# web/: npm ci && npm run build
python scripts/build_wheel.py
python scripts/verify_wheel.py dist/agenttrace-0.1.0-py3-none-any.whl
```

强杀测试使用 Windows TerminateProcess / POSIX SIGKILL，不执行 finally 或 atexit；崩溃后
直接用 QueryStore 只读连接读取，未先启动 SDK 做恢复写入，也没有将“正常退出”当强杀。

安装包检查另发现 setuptools 的本地增量 build 目录会保留旧哈希 JS，导致新 wheel 混入
旧资源。新增 `build_wheel.py` 使用干净暂存目录构建，不删除已有源码或工作目录；
`verify_wheel.py` 要求资源集合与当前前端产物完全一致，既检查遗漏也检查陈旧文件。
最终 wheel 为 `dist/agenttrace-0.1.0-py3-none-any.whl`（395941 bytes），资源集合检查和
`python -I -S` 零依赖 SDK/Mock/SQLite 冒烟均通过。

## 4. 性能矩阵：明确仍未通过的场景

每个场景 20 次，两种模式、入口与多步骤、0/20/200ms 等待负载；基线与埋点交错并交替先后
顺序。多步骤含根任务、决策步骤、两个工具和两次 LLM；不访问网络。完整均值/P95/最大值、
排空状态和诊断统计见 [原始矩阵](performance-comparison.json)。

| 模式 | 场景 | 等待负载 | 平均额外耗时 | 相对开销 | <=10% |

| durable | 入口 | 0 ms | 1.5662 ms | 206081.58% | 否 |
| durable | 入口 | 20 ms | 1.9221 ms | 9.42% | 是 |
| durable | 入口 | 200 ms | 2.5157 ms | 1.26% | 是 |
| durable | 多步骤 | 0 ms | 8.0451 ms | 505979.87% | 否 |
| durable | 多步骤 | 20 ms | 8.3243 ms | 39.93% | 否 |
| durable | 多步骤 | 200 ms | 10.4053 ms | 5.18% | 是 |
| async | 入口 | 0 ms | 0.1438 ms | 36397.47% | 否 |
| async | 入口 | 20 ms | 0.6839 ms | 3.35% | 是 |
| async | 入口 | 200 ms | 0.3787 ms | 0.19% | 是 |
| async | 多步骤 | 0 ms | 0.3278 ms | 27897.02% | 否 |
| async | 多步骤 | 20 ms | 0.5851 ms | 2.81% | 是 |
| async | 多步骤 | 200 ms | 0.7352 ms | 0.37% | 是 |

0ms 空任务的基线接近零，因此百分比很大，绝对耗时更有解释力；仍保留数据，没有删除超标
场景。async 的业务耗时不包括计时外排空，不能据此说明总 I/O 成本消失。
**NFR-1 仍是部分验证，默认持久模式的短任务尚未达到 10%。** 当前没有为了性能暗改持久性默认
或验收阈值。后续可研究单库持久化缓冲、批量确认和更真实 Agent 负载；需继续保留强杀证据。

1000 条任务、每条 6 Span，重复查询 10 次：SQLite 平均 **8.7409 ms**，最大 11.3256 ms；
ASGI 测试客户端（含 API 序列化及 JSON 读取）平均 **25.7948 ms**，最大 30.1519 ms。
ASGI 客户端不是网络链路；浏览器采样是分页首屏，不是一次渲染 1000 行。
